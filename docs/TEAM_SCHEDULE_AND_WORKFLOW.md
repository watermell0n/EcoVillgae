# 이코빌리지 팀 일정·협업 방식

- 기준일: 2026-07-30
- 개발 기준 브랜치: `develop`
- 목적: 팀원이 같은 기준선에서 병렬 작업하고 공용 파일 충돌을 줄이는 것

## 1. 현재 진행상황

저장소 기준으로 공통 환경 설정, OpenAPI·AsyncAPI 계약, API 필드 매핑, 85개 테이블의 Flyway
`V1_1`~`V1_13`, DBT-001~020 구현이 완료되었습니다. Docker 사용 Jenkins의
Testcontainers 21개 전체 실행, 계약 기반 인터페이스 생성, 앱·웹·AI
서비스 구현과 서비스·E2E 인수 테스트가 남아 있습니다.

Jira 상태와 작업 수는 수시로 바뀌므로 이 문서에 고정하지 않습니다. 담당자는 작업
시작·종료 시 Jira의 활성 스프린트를 현재 기준으로 확인합니다.

### 1.1 2026-08-01 클라이언트 기준 정정

- 학생은 학교 지급 Galaxy Tab용 React Native·Expo 앱을 사용합니다.
- 교사는 별도 모바일 앱 없이 Next.js 웹의 수업 진행 화면과 관리 화면을 사용합니다.
- 학생 앱 코드는 `student-app/expo/` 하나이며 신규 기능은 모두 여기서 구현합니다.
- 역할별 전환 작업과 완료 조건은 [학생 앱·교사 웹 전환 계획](CLIENT_ARCHITECTURE_TRANSITION.md)을 따릅니다.

반영합니다.

## 4. 브랜치 규칙

- `master`: 검증을 마친 배포 가능한 릴리스 이력을 보존합니다.
- `develop`: 다음 릴리스의 개발 통합 기준선이며 일반 작업 MR의 대상입니다.
- 모든 팀원은 최신 `develop`에서 본인 작업 브랜치를 만듭니다.
- 권장 이름은 `feat/<Jira번호>-<짧은설명>`입니다. 버그와 독립 문서는 각각
  `fix/*`, `docs/*`를 사용합니다.
- 팀원은 다른 사람의 개인 개발 브랜치에서 분기하지 않습니다.

```bash
git switch develop
git pull --ff-only origin develop
git switch -c feat/S15P11B201-198-ai-thresholds
```

작업이 끝나면 원격 브랜치에 푸시하고 `develop` 대상 Merge Request를 만듭니다.
한 브랜치와 MR에는 가능한 한 Jira 작업 하나만 포함합니다.

기존 개인 통합 브랜치의 진행 중 변경은 기능 단위로 정리해 `develop` 대상 MR로
올리고, 이후 신규 작업은 모두 `develop`에서 분기합니다.

## 5. 하루 작업 흐름

### 시작

1. Jira에서 본인 작업 하나를 `진행 중`으로 바꿉니다.
2. `develop`을 최신화하고 본인 브랜치에 반영합니다.
3. 오늘 변경할 경로와 공용 계약 변경 여부를 팀에 공유합니다.

### 작업 중

1. 자신의 담당 디렉터리에서 작업합니다.
2. API가 필요하면 화면에서 임의 응답을 확정하지 않고 계약 변경을 먼저 제안합니다.
3. 공용 파일 변경이 필요하면 담당자와 순서를 정합니다.
4. 큰 변경 하나보다 검토 가능한 작은 커밋을 남깁니다.

### 종료

1. 테스트·정적 검사를 실행합니다.
2. Jira에 커밋, 산출물과 남은 위험을 기록합니다.
3. 완료 조건을 충족했을 때만 `완료`로 변경합니다.
4. 다음 사람이 이어야 하는 내용은 MR 설명에 남깁니다.

## 6. 충돌 방지 규칙

1. 필요한 공통 골격이 `develop`에 반영되기 전에 의존하는 구현 브랜치를 만들지 않습니다.
2. 동일 파일을 둘 이상이 동시에 수정하지 않습니다.
3. OpenAPI·AsyncAPI 변경은 구현보다 먼저 병합합니다.
4. Flyway 적용 이력이 있는 파일은 수정하지 않고 새 버전을 추가합니다.
5. 다른 사람 변경을 덮는 강제 푸시를 사용하지 않습니다.
6. 오래 작업한 브랜치는 매일 `develop`을 반영합니다.
7. 바이너리 캐릭터 원본은 한 명이 편집하고 최적화 결과를 별도 경로에 둡니다.

## 7. Merge Request 완료 기준

- 관련 Jira 번호와 변경 이유가 있다.
- 영향받는 앱·API·DB·이벤트·문서가 표시되어 있다.
- 실행한 테스트와 결과가 있다.
- 비밀정보와 학생 개인 식별정보가 없다.
- 공통 계약 변경 시 RTM과 구현 계약을 함께 확인했다.
- 리뷰가 끝나기 전 `develop`이나 `master`에 직접 병합하지 않는다.

## 8. 팀 통합일과 master 반영

개별 기능이 끝날 때마다 `master`에 병합하지 않습니다. 팀 통합은 다음 순서로
진행합니다.

1. 통합 시작 전에 `master`의 최신 변경을 `develop`에 반영합니다.
2. 각 팀원의 작업 브랜치를 `develop` 대상 MR로 하나씩 병합합니다.
3. 충돌은 관련 담당자가 변경 의도를 확인해 작업 브랜치에서 해결합니다.
4. 각 병합 후 해당 영역 테스트를 실행하고, 모든 병합 후 `develop` 전체 CI와
   주요 사용자 흐름 스모크 테스트를 실행합니다.
5. 모든 검증이 통과하고 심각한 결함이 없을 때만 `develop`에서 `master`로 MR을
   만들어 안정 버전으로 승격합니다.

현재 MVP 통합에서는 별도 `release/*` 브랜치를 강제하지 않습니다. 통합 중 발견한
오류는 `develop`에서 수정하고 처음부터 다시 검증합니다.

운영 중 긴급 수정은 `master`에서 `hotfix/*`를 분기하고, 검증 후 `master`와
`develop` 양쪽에 병합합니다.
