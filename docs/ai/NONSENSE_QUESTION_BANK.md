# 넌센스 문제은행 설계안

> 상태: **초안 v0.1 / 미구현.** 데이터 파일만 만들어 뒀고 코드는 손대지 않았습니다.
> 채택 여부는 팀이 정합니다.

## 왜 AI 생성을 그만두자는 건가

골든셋 두 번(수정 전 `run-c-both`, 수정 후 `run-c2-postfix`)을 돌린 결과입니다.

| 항목 | 경제 | 넌센스 |
|---|---|---|
| 생성 성공 | 6/6 | 6/6 |
| 내용이 쓸 만한가 | **대체로 좋음** | 성립률 대략 1/3 |
| 반복되는 실패 | 없음 | 없는 낱말 지어내기, 소리 안 겹치는 연상 |

프롬프트에 성립 조건을 못박은 뒤 **나아지긴 했습니다.** `후루룩국수`→`후루룩`, `화들짝밥`→`꿀떡`처럼 실재하는 낱말을 고르기 시작했고, 오답 설계에도 규칙을 씁니다.

그래도 한계가 분명합니다.

- **색깔 소재는 두 번 다 전멸했습니다.** 색 이름에는 걸 만한 말장난이 거의 없습니다. 팀이 고른 원본 40개에도 색깔 말장난은 하나도 없습니다. 만들 수 없는 것을 만들라고 시킨 셈입니다.
- 규칙을 넣어도 `가만의사`, `침대사` 같은 조어가 계속 나옵니다. **모델이 한국어 말장난을 창작하는 능력 자체가 약합니다.**

### 결정적인 차이

|  | 경제 퀴즈 | 넌센스 퀴즈 |
|---|---|---|
| 목적 | 교사의 **학습목표를 평가** | **재미** |
| 매번 달라야 하나 | 예. 학급·단원마다 다름 | 아니오 |
| AI가 꼭 필요한가 | **그렇다** | **아니다** |

넌센스는 미리 만들어 둔 문항을 돌려 써도 목적을 100% 달성합니다.
그러면 품질이 보장되고, AI 호출 비용과 실패 위험이 사라집니다.

## 두 가지 구조

| | A. DB 테이블 | **B. 리소스 파일 (추천)** |
|---|---|---|
| 저장 | 새 테이블 + Flyway `V1_32` | `resources/quiz/nonsense-bank-v1.json` |
| 문항 수정 | 관리 화면 또는 SQL | 파일 편집 후 배포 |
| 교사가 은행을 늘림 | 가능 | 불가 |
| 작업량 | 마이그레이션 + 엔티티 + 저장소 + 서비스 + API + UI | **서비스 + API + UI** |
| 되돌리기 | 마이그레이션 되돌림 필요 | 파일 삭제 |

**B를 추천합니다.** 문항이 40개 안팎으로 고정이고 교사가 은행 자체를 늘릴 일이 없는 MVP 단계에서는 테이블을 만들 이유가 없습니다. 나중에 A로 옮기고 싶으면 이 JSON을 그대로 시드로 쓰면 됩니다.

## 데이터

[`backend/src/main/resources/quiz/nonsense-bank-v1.json`](../../backend/src/main/resources/quiz/nonsense-bank-v1.json) — **24문항 초안**을 만들어 뒀습니다.

원본 40개에서 아래를 뺐습니다.

| 뺀 이유 | 해당 문항 |
|---|---|
| 폭력·비하 소재 (안전 검사에도 걸림) | 칠레(폭력배), 창피해(창으로 찌름), 치과(이상한 사람들) |
| 연예인 이름 | 태연 |
| 프롬프트 예시로 이미 씀 | 후다닥, 호주머니, 고등어, 인수분해 |
| 말장난이 약하거나 뜻이 불분명 | 타이타닉, 미소/당기소, 책피자, 십구만, 베를린 |

한 문항의 생김새입니다.

```json
{
  "id": "nb-003",
  "grades": [4, 5, 6],
  "theme": "음식",
  "pun_type": "소리 겹치기",
  "question": "도둑이 가장 싫어하는 아이스크림은 무엇일까요?",
  "choices": [
    { "key": "A", "text": "월드콘" },
    { "key": "B", "text": "메로나" },
    { "key": "C", "text": "누가바" },
    { "key": "D", "text": "빠삐코" }
  ],
  "correct_choice_key": "C",
  "explanation": "'누가바'는 아이스크림 이름이면서 '누가 봐'처럼 들려요. …"
}
```

- `grades` — 그 학년에 맞는 문항만 걸러 주기 위한 값입니다. 한자어가 들어간 것(최저임금, 정삼각형, 수학익힘책)은 6학년만 달았습니다.
- **오답은 원본에 없어서 새로 만들었습니다.** 정답과 같은 부류의 낱말로 채웠고(아이스크림 답에는 아이스크림 오답), 교사 검토가 가장 필요한 부분입니다.
- `pun_type` — 나중에 "같은 유형이 몰리지 않게" 뽑을 때 쓸 수 있습니다.

## 가져오기 흐름

새 도메인을 만들 필요가 없습니다. **AI 초안 저장과 똑같은 경로**를 씁니다.

```
교사가 "넌센스 문제 가져오기" 클릭 (개수 지정)
  → 은행에서 학년에 맞는 문항 필터
  → 이 학급에 이미 있는 문항 제외
  → 남은 것 중 무작위 N개
  → QuizQuestionCommandService.edit(CREATE) 로 학급에 저장
  → 상태는 DRAFT, 교사 승인 후 공개
```

[`QuizDraftService.persistDrafts`](../../backend/src/main/java/com/b201/ecovillage/ai/application/QuizDraftService.java)가 이미 이 방식으로 AI 결과를 저장합니다. 그대로 흉내내면 됩니다.

### 중복 방지

`QuizQuestion`에는 출처를 적을 칸이 없습니다. 컬럼을 추가하면 마이그레이션이 필요하니, **가져올 때 해당 학급의 기존 문항 본문과 대조해 제외**하는 방식을 권합니다. 스키마 변경이 없고 24문항 규모에서는 충분히 빠릅니다.

가져갈 게 남지 않으면 "더 가져올 문제가 없습니다"로 알려 줍니다.

### 승인 흐름

AI 초안은 `requireReview`로 검토 필수 상태가 됩니다. 은행 문항은 **사람이 이미 검토한 것**이므로 그대로 `DRAFT`로 두고 교사가 바로 공개할 수 있게 하는 편이 자연스럽습니다. (팀 결정 필요)

## 교사 화면

지금 [`QuizDraftWorkspace.tsx`](../../teacher-web/app/ai/QuizDraftWorkspace.tsx)에서 분류를 `ECONOMY` / `NONSENSE` 중에 고릅니다.

| 고른 분류 | 바뀌는 화면 |
|---|---|
| `ECONOMY` | 지금 그대로 (주제·학습목표 입력 → AI 생성) |
| `NONSENSE` | **주제·학습목표 입력칸을 숨기고**, 학년과 개수만 받아 "문제 가져오기" |

넌센스는 학습목표를 평가하는 게 아니라서 그 입력칸이 원래 의미가 없었습니다.

### OX 넌센스 문제 정리

골든셋의 미해결 질문이었는데 **답이 나왔습니다.** OX 넌센스는 세 번 중

- 1회 스키마 오류로 생성 실패
- 1회 3문항 중 2개가 "말장난이 성립하지 않는다"를 정답으로 삼는 도피 문항
- 1회만 그럭저럭

**은행은 객관식만 담고, 교사 화면에서 넌센스 × OX 조합을 막는 것**을 권합니다. "정답이 O냐 X냐"로는 언어유희가 성립하기 어렵다는 것이 데이터로 확인됐습니다.

## AI 넌센스 생성은 어떻게 하나

| 안 | 내용 |
|---|---|
| **끄기 (추천)** | 넌센스는 은행만. 실패·품질 편차가 사라짐 |
| 남기기 | 은행이 바닥났을 때만 AI 사용. 경로가 둘이라 복잡해짐 |

끄더라도 `nonsense.txt`와 프롬프트 분리는 **지우지 마세요.** 되살릴 때 필요하고, 지금 넣은 성립 조건은 나중에 은행을 늘릴 때 사람에게도 좋은 기준입니다.

## 남은 작업

| # | 할 일 | 담당 | 예상 |
|---|---|---|---|
| 1 | 24문항 **교사 검토** (특히 오답) | 사람 | 40분 |
| 2 | 원본 40개 중 뺀 것 재검토, 필요하면 추가 | 사람 | 30분 |
| 3 | 은행 로더 + 가져오기 서비스 | BE | 2~3시간 |
| 4 | 가져오기 API 1개 | BE | 1시간 |
| 5 | 교사 화면 분기 (넌센스면 가져오기) | FE | 2시간 |
| 6 | 넌센스 × OX 막기 | FE | 30분 |

**1번이 먼저입니다.** 오답을 제가 새로 만들었기 때문에, 사람이 한 번 훑기 전에는 코드를 붙일 값어치가 없습니다.

## 이 설계가 해결하지 못하는 것

- **문항이 24개뿐입니다.** 한 학급에서 여러 번 쓰면 금방 바닥납니다. 3~5개씩 쓴다면 대여섯 번 분량입니다.
- 학생이 이미 본 문제를 다시 볼 수 있습니다. 학급 단위 중복만 막고 학생 단위는 보지 않습니다.
- 새 문항은 사람이 써야 합니다. 다만 원본 40개를 만든 것처럼 어려운 일은 아닙니다.
