# 규칙 엔진 추천·판정 상세 명세

- 규칙 엔진 명세 버전: `rule-engine-v1`
- 기준일: 2026-07-31
- 상태: Spring 구현 착수 전 상세 명세 확정
- 대상: 방 생성·상품 등록·퀴즈 등록 시 규칙 기반 추천값과 시작 전 점검을 계산하는 Spring 규칙 엔진

이 문서는 **Spring 규칙 엔진이 계산하는 6종 추천값과 `PASS·WARN·BLOCK` 판정**의
기준값·공식·허용 범위·반올림·사유 코드를 확정합니다. AI 서비스는 이 값을 바꾸지 않고
교사에게 설명만 합니다.

상위 문서: [AI 활용 방향](../AI_DIRECTION.md) → [내부 AI API 계약](INTERNAL_API_CONTRACT.md) ·
[경제 지표·임계값](METRICS_AND_THRESHOLDS.md) · [경제 설정 추천·시작 전 점검](SETUP_PRECHECK.md).
값이 충돌하면 `docs` 폴더 문서를 정본으로 사용합니다.

## 0. 먼저 읽는 쉬운 설명

처음 보는 사람도 이해할 수 있게 핵심 용어부터 정리합니다.

| 용어 | 쉬운 뜻 |
| --- | --- |
| **기준 급여 (S_base)** | 교실 화폐는 교사가 이름 붙이는 가상 돈이라 절대 가치가 없습니다. 그래서 계산의 "기준 눈금"이 되는 대표 급여 하나를 `1,000`으로 정하고, 세금·물건값·보상은 모두 이 값에 대한 비율로 계산합니다. `1,000`이라는 숫자 자체보다 "기준"이라는 점이 중요합니다. |
| **bps** | 비율을 소수점 없이 정수로 쓰는 단위입니다. `100 bps = 1%`, `300 bps = 3%`, `10,000 bps = 100%`. 이 프로젝트는 돈 계산에 소수점을 쓰지 않기로 정해서(`DM-004`) 3%를 `300`으로 저장합니다. 읽을 때는 "뒤 두 자리 떼고 %"로 보면 됩니다. |
| **발행 / 회수** | 발행은 급여·보상처럼 시스템이 학생에게 **주는** 돈, 회수는 세금·상점 결제처럼 시스템이 **거둬들이는** 돈입니다. 둘이 크게 어긋나면 경제가 망가집니다. |
| **후보 (candidate)** | 규칙 엔진이 계산해 교사에게 추천하는 값 하나(예: "연필 가격 290"). 교사가 확인·수정합니다. |
| **점검 (check)** | 설정이 정상인지 검사한 결과. `PASS`(정상)·`WARN`(주의)·`BLOCK`(시작 불가) 세 단계입니다. |

**한 줄 요약**: 규칙 엔진은 "기준 급여 1,000"을 눈금 삼아 급여·세율·금리·상품값·퀴즈 보상을
계산하고, 값이 안전 범위 안인지 `PASS·WARN·BLOCK`으로 판정합니다.

## 1. 추천하는 6종 값과 시점

| 순번 | 추천값 | `target_type` | 단위 | 언제 | `target_id` |
| --- | --- | --- | --- | --- | --- |
| 1 | 역할 급여 | `ROLE_SALARY` | 금액 | 방 생성(개설 마법사) | `null` |
| 2 | 소득세율 | `INCOME_TAX_RATE` | `RATE_BPS` | 방 생성 | `null` |
| 3 | 예금 금리 | `DEPOSIT_RATE` | `RATE_BPS` | 방 생성 | `null` |
| 4 | 대출 금리 | `LOAN_RATE` | `RATE_BPS` | 방 생성 | `null` |
| 5 | 상품 가격 | `PRODUCT_PRICE` | 금액 | 교사가 상품 등록·수정 | 상품 UUID |
| 6 | GAME 퀴즈 보상 | `GAME_REWARD` | 금액 | 교사가 퀴즈 세션 설정 | 세션·초안 UUID |

- 방 생성 때 1~4를 한 번에, 상품 등록 때 5를, 퀴즈 등록 때 6을 추천합니다(`AI-009`).
- 최종 값은 교사가 확인·수정하며, 저장 시 핵심 API가 다시 검증합니다.
- 후보의 필드(값·범위·단위·근거)는 `SetupCandidate` 계약과 정확히 일치합니다
  ([내부 OpenAPI](../../contracts/ai-internal-openapi.yaml)).

## 2. 입력값

규칙 엔진의 **내부 입력**은 AI에 넘기는 `SetupContext`보다 넓습니다. 규칙 엔진이 먼저
계산하고, AI에는 계산이 끝난 후보와 슬림한 문맥만 전달합니다(계약 변경 없음).

| 문맥 | 필요한 입력 |
| --- | --- |
| 방 생성 (`CLASSROOM_SETUP`) | 학년(4·5·6), 코스 규모 라벨, 실제 운영기간(일), 예상 학생 수, 활성 모듈, 급여 지급 주기·역할 구성(역할별 상대 크기), 화폐 단위명 |
| 상품 등록 (`PRODUCT_DRAFT`) | 상품 종류, 재고 수량, 예상 구매 빈도(주기당), 부가세율, 현재 급여·세율 |
| 퀴즈 등록 (`QUIZ_SESSION_DRAFT`) | 실행 모드(GAME·TEST), 분류(경제·넌센스), 문항 수, 예상 참가자, 예상 실행 횟수, 현재 발행 예산 |

- 학년은 4·5·6만 허용합니다.
- **지급 횟수 `N_pay`**: 교사가 급여 주기를 지정하면 그 값을, 없으면 규모 라벨 기본값을 씁니다.

| 규모 라벨 | `N_pay` 기본값 |
| --- | ---: |
| `ONE_WEEK` | 1 |
| `ONE_MONTH` | 4 |
| `ONE_SEMESTER` | 16 |
| `ONE_SHOT` | 해당 없음(지갑·보상 없음) |

## 3. 확정 상수 (rule-engine-v1)

아래 값이 모든 계산의 기준입니다. 초기 휴리스틱이며 운영 평가로 새 버전을 낼 수 있지만,
이미 끝난 실행의 값은 바꾸지 않습니다.

### 3.1 급여·격차

| 항목 | 값 | 설명 |
| --- | --- | --- |
| 기준 급여 `S_base` | 1,000 | 가중치 1.0 역할의 주기당 급여. 계산의 기준 눈금 |
| 역할 가중치 범위 | 초4 0.9~1.2 / 초5 0.8~1.4 / 초6 0.7~1.7 | 저학년은 격차 작게, 고학년은 크게 |
| 역할 격차 상한(최고÷최저) | 초4 1.5 / 초5 2.0 / 초6 2.5 | 넘으면 `WARN` |
| 급여 하한 | 100 | 이보다 낮은 급여는 만들지 않음 |

### 3.2 세율·금리 (단위 bps)

| 항목 | 값 | 설명 |
| --- | --- | --- |
| 기준 소득세율 | 초4 300(모듈 활성 시만) / 초5 500 / 초6 1,000 | 급여에서 떼는 비율 |
| 소득세율 범위 | 초4 200~500 / 초5 300~800 / 초6 500~1,500 | 교사 조절 폭 |
| 기준 예금 금리(만기 1회) | 300 | 만기 시 원금의 3% |
| 예금 금리 범위 | 100~600 | 만기 1~6% |
| 예대 최소 스프레드 | +200 | 대출 금리는 항상 예금+2%p 이상 |
| 기준 대출 금리 | 예금 선택값+400 | 예금 3%면 대출 7% |
| 대출 금리 범위 | 예금 선택값+200 ~ 예금 선택값+900, 상한 1,500 | 예금보다 비쌈 |

- 금리는 **만기 1회(상품 기간) 기준**입니다. 연환산이 아닙니다.
- 초4는 세금 모듈을 켠 경우에만 세율 후보를 만듭니다.
- 대출 금리 후보는 **초5·초6의 `ONE_SEMESTER`(1학기)** 에서만 만듭니다(`FIN-008`, 코스 추천 기준).

### 3.3 상품 가격·퀴즈 보상

| 항목 | 값 | 설명 |
| --- | --- | --- |
| 상품 가격 비율(종류별) | 소모성 디지털 0.15 / 실물 0.30 / 캐릭터 0.50 | 세후 급여 1회분 대비 |
| GAME 보상 기준 | 경제 = `S_base`×0.05 = 50 / 넌센스 = 경제×0.30 = 15 | 참여 보상(모두 동일 지급) |
| 보상 총발행 상한 | 발행 예산의 30% (3,000 bps) | 넘으면 하향(`REWARD_ISSUANCE_SHARE_BPS`) |
| 넌센스 하드캡 | 경제 보상의 30% 이하 | `QZ-005` |

### 3.4 정수·반올림·범위 폭

| 항목 | 값 | 설명 |
| --- | --- | --- |
| 금액·금리 저장형 | 정수 | 금액은 최소 화폐단위, 비율은 bps(`DM-004`) |
| 반올림 단위 | 금액 10단위 / 세율·금리 50 bps | 어중간한 숫자 대신 깔끔하게 |
| 반올림 방식 | 가까운 눈금으로, 정확히 가운데면 올림 | 예: 285 → 290 |
| 금액 하한 | 급여 100 / 가격·보상 10 | 0·1 방지 |
| 추천 범위 폭(금액계, 학년 차등) | 초4 ±10% / 초5 ±15% / 초6 ±20% | 급여·상품 가격·보상의 `min`~`max` |
| 세율·금리 범위 | 3.2의 고정 bps 범위 | 금액계 ±%가 아니라 bps 범위를 씀 |

## 4. 계산 공식

기호: `round10(x)`=10단위 반올림, `round50(x)`=50bps 단위 반올림, `clamp(x,a,b)`=a~b로 자르기,
`w(g)`=학년별 범위 폭(초4 0.10·초5 0.15·초6 0.20).

### 4.1 예산 프레임 (먼저 계산)

모든 금액을 학급 예산 비율로 검증하기 위해 다음을 먼저 구합니다.

- 세후 급여 1회분: `net_pp = round10( S_base × (1 − 세율bps / 10,000) )`
- 평균 급여: `avg_salary = round10( S_base × 역할 가중치 평균 )`
- 발행 예산: `B_issue = avg_salary × N_pay × 학생수 (+ 예상 보상 발행)`
- 세금 회수: `B_tax = avg_salary × 세율bps / 10,000 × N_pay × 학생수`
- 회수/발행 균형: `balance = (B_tax + 예상 상점 소비) / B_issue`

### 4.2 역할 급여 `ROLE_SALARY`

```
proposed = clamp( round10( S_base × weight(role) ), 100, ∞ )
min      = max( 100, round10( proposed × (1 − w(g)) ) )
max      =            round10( proposed × (1 + w(g)) )
reason   = [SALARY_ROLE_WEIGHT, SALARY_GRADE_PROFILE]
```

- `weight(role)`는 교사가 정한 역할 상대 크기이며 학년 허용 가중치 범위로 제한합니다.

### 4.3 소득세율 `INCOME_TAX_RATE`

```
세금 모듈 비활성 → 후보 없음
proposed = round50( clamp( 기준세율(g), 학년 세율 범위 ) )
min, max = 학년 세율 범위 (3.2)
reason   = [TAX_GRADE_PROFILE, TAX_RECOVERY_BALANCE]
```

### 4.4 예금 금리 `DEPOSIT_RATE`

```
proposed = round50( 300 )           # 범위 100~600
min, max = 100, 600
reason   = [DEPOSIT_TERM_BASED, DEPOSIT_GRADE_BAND]
```

### 4.5 대출 금리 `LOAN_RATE`

```
초5·초6 ONE_SEMESTER 아니면 → 후보 없음
deposit  = 확정된 예금 금리
proposed = round50( clamp( deposit + 400, deposit + 200, min(deposit + 900, 1500) ) )
min      = deposit + 200            # 예대 최소 스프레드
max      = min( deposit + 900, 1500 )
불변식   : proposed ≥ deposit + 200
reason   = [LOAN_DEPOSIT_SPREAD, LOAN_GRADE_BAND]
```

### 4.6 상품 가격 `PRODUCT_PRICE`

```
무료·비매품 → 후보 없음
freq        = 예상 구매 빈도(주기당, 없으면 1)
base        = net_pp × ratio(종류) / freq
scarcity    = 재고 < 학생수 ? clamp( 1 + 0.2 × (1 − 재고 / 학생수), 1.0, 1.2 ) : 1.0
proposed    = clamp( round10( base × scarcity ), 10, ∞ )
min, max    = round10( proposed × (1 ∓ w(g)) ), min ≥ 10
reason      = [SALARY_PRICE_BALANCE, PRODUCT_KIND_RATIO, PRODUCT_STOCK_SCARCITY]
```

- 재고가 학생 수보다 적으면(귀한 물건) 최대 +20%까지 가격을 올립니다. 재고가 충분하면 보정 없음.
- 부가세는 가격과 별도로 다룹니다(`ECO-005`).

### 4.7 GAME 퀴즈 보상 `GAME_REWARD`

```
TEST · 모든 1회 코스 · 지갑 미사용 → 후보 없음
base      = 경제 ? S_base × 0.05 : S_base × 0.05 × 0.30      # 50 또는 15
total     = base × 예상참가자 × 예상실행횟수
상한 초과 : total > 0.30 × B_issue 이면 base 를 상한에 맞춰 하향
넌센스캡  : 넌센스 base ≤ 경제 base × 0.30
proposed  = clamp( round10( 조정된 base ), 10, ∞ )
min, max  = round10( proposed × (1 ∓ w(g)) ), min ≥ 10
reason    = [REWARD_PARTICIPATION_BASE, REWARD_ISSUANCE_SHARE] (넌센스면 + REWARD_NONSENSE_CAP)
```

## 5. 값들 사이의 관계

- **급여 → 세율 → 실수령 → 상품 가격 → 보상** 순으로 이어집니다. 세금은 급여에 부과되고,
  상품 가격은 세후 급여를 기준으로, 보상은 급여의 소액(발행의 30% 이내)으로 정합니다.
- **예금 < 대출**: 대출 금리는 항상 예금 금리보다 최소 200 bps 높습니다. 어기면 `BLOCK`.
- 이 관계가 맞아야 발행(급여+보상)과 회수(세금+소비)가 균형을 이룹니다. 어긋나면 `WARN`.

## 6. 시작 전 점검: PASS·WARN·BLOCK

경제교실은 생성 즉시 사용 가능하지만, 첫 `OPEN`·화폐 변경 활동 전에 정합성을 점검합니다.
`overall_severity`는 가장 높은 심각도(`BLOCK > WARN > PASS`)입니다.

### 6.1 BLOCK — 수정 전 시작 금지

| 사유 코드 | 조건 |
| --- | --- |
| `REQUIRED_VALUE_MISSING` | 필수 입력·후보 누락(활성 모듈 대상 값, 급여 등) |
| `VALUE_OUT_OF_RANGE` | 확정값이 허용 `min`~`max` 밖 |
| `FORBIDDEN_REWARD_CONTEXT` | `TEST`·1회 코스에 화폐 보상 후보가 있음(`CRS-002`·`QZ-004`) |
| `LOAN_DEPOSIT_SPREAD_VIOLATION` | 대출 금리 < 예금 금리 + 200 bps |
| `CURRENCY_NAME_MISSING` | 지갑 코스인데 화폐 단위명이 없음 |

### 6.2 WARN — 교사 확인 후 진행 가능

| 사유 코드 | 조건 |
| --- | --- |
| `ISSUANCE_RECOVERY_IMBALANCE` | 회수/발행 비율이 권장 밴드(30%~120%) 밖 |
| `OUT_OF_RECOMMENDED_BAND` | 권장 범위 밖이지만 허용 `min`~`max` 안 |
| `ROLE_SALARY_GAP_EXCESSIVE` | 최고÷최저 급여가 학년 격차 상한 초과 |
| `REWARD_SHARE_HIGH` | 보상 총발행이 발행 예산의 25% 초과(30% 도달 전 경고) |
| `NO_RECOVERY_CHANNEL` | 세금·상점 등 회수 수단이 하나도 없음 |

### 6.3 PASS

| 사유 코드 | 조건 |
| --- | --- |
| `REQUIRED_VALUES_PRESENT` | 필수값이 모두 준비됨 |
| `VALUES_WITHIN_RANGE` | 모든 확정값이 허용 범위 안 |
| `BUDGET_BALANCED` | 발행·회수 균형이 권장 밴드 안 |

## 7. 데이터 부족·기능 비활성 처리

- 시작 전 점검은 운영 분석의 **최소 학생 5명·거래 10건 규칙을 적용하지 않습니다**
  (`METRICS_AND_THRESHOLDS.md` §8). 현재 설정만으로 정적 점검합니다.
- **모듈 비활성** → 그 대상 후보를 아예 만들지 않습니다(오류가 아님). 예: 세금 모듈 off →
  `INCOME_TAX_RATE` 없음, 예금 모듈 off → `DEPOSIT_RATE` 없음.
- **필수 입력 미입력** → 계산 불가이므로 `REQUIRED_VALUE_MISSING`으로 `BLOCK`.
- **`ONE_SHOT`·모든 1회 코스** → 후보를 전혀 만들지 않고, 보상이 없는지 점검만 합니다.
- AI가 꺼져 있거나 모델 호출이 실패해도 이 규칙 기반 값과 점검 결과는 그대로 반환합니다.

## 8. 설정 변경·재계산 시점

급여·세율·금리, 예상 학생 수, 실제 운영기간, 활성 모듈, 상품 가격·재고, 퀴즈 보상 중
하나라도 바뀌면 이전 점검의 입력 해시가 달라지므로 **점검 결과를 만료시키고 다시 계산**합니다
(`AI_DIRECTION` §3.2와 동일). 점검은 미래를 예측하지 않고 현재 설정만 봅니다.

## 9. 대표 계산 예시 (초5 · 1달 · 24명)

역할 3개 가중치 0.8 / 1.0 / 1.3 → 급여 800 / 1,000 / 1,300 (격차 1.625 ≤ 2.0, 정상).

| 추천값 | 계산 | 결과 | 범위(±15%) |
| --- | --- | --- | --- |
| 급여(기준 역할) | `round10(1,000×1.0)` | 1,000 | 850 ~ 1,150 |
| 소득세율 | 기준 초5 | 500 bps(5%) | 300 ~ 800 |
| 예금 금리 | 기준 | 300 bps(3%) | 100 ~ 600 |
| 대출 금리 | 1달이라 후보 없음(1학기만) | — | — |
| 세후 급여 1회 | `1,000×(1−0.05)` | 950 | — |
| 상품 가격(실물·재고24·빈도1) | `950×0.30×1.0` | 290 | 250 ~ 330 |
| GAME 보상(경제) | `1,000×0.05` | 50 | 40 ~ 60 |

보상 발행 점검: `50 × 24명 × 8회 = 9,600`, 발행 예산 `≈ 1,033 × 4 × 24 ≈ 99,200`,
비율 `9.7% < 30%` → 정상.

## 12. FastAPI SETUP_PRECHECK로 넘기는 값과 책임 경계

규칙 엔진이 **후보(`candidates`) + 점검(`checks`) + `overall_severity`를 모두 계산**하고,
FastAPI는 이를 **그대로 인용해 설명만** 합니다.

| 규칙 엔진(Spring)이 소유 | FastAPI(AI)가 하는 일 |
| --- | --- |
| `action_id`·`target_type`·값·`min`·`max`·단위·`reason_codes` 계산 | 값을 바꾸지 않고 교사용 설명 생성 |
| `PASS·WARN·BLOCK` 판정과 `overall_severity` | 판정 심각도·근거를 인용해 이유 설명 |
| 후보를 만들지/생략할지 결정(모듈·코스) | 받은 후보만 설명, 새 후보 생성 금지 |

- 후보·점검을 누락·추가·변조하면 AI 응답은 실패 처리됩니다(`SETUP_PRECHECK.md`).
- 모든 성공 결과는 `REVIEW_REQUIRED`이며 교사 확인 전 반영되지 않습니다.
- 실제 저장·정책 반영은 핵심 API가 최신 정책으로 다시 검증합니다(`AI-002`·`AI-003`·`FIN-011`).
