# 2026-07-16 교사·학생 2일 통합 여정 개발 계획

## 1. 목표

이 문서의 목표는 관리자 기능을 제외하고, 교사와 학생이 여정지도 축약본의 1일차·2일차 흐름을 로컬 환경에서 실제 API와 PostgreSQL 데이터로 끝까지 실행할 수 있게 하는 것이다.

기존 계획은 1일차 퀴즈·소득 정산·상점 구매까지의 짧은 데모를 목표로 했지만, 현재 목표는 다음 전체 수직 흐름으로 확장한다.

```text
교사 방 생성·참여 코드 확인
→ 학생 참여 코드 입장·최초 계정 설정
→ 1일차 퀴즈
→ 소득·세금 정산
→ 월급명세서와 금융지식 교육
→ 상점·예금·투자 안내
→ 자유 경제활동
→ 1일차 결과 확인·마감
→ 2일차 재로그인
→ 예금·투자·금융세 정산
→ 2일차 복습 퀴즈와 보상
→ 금융세·인플레이션 교육
→ 물가상승 적용·최종 소비
→ 공동기금 사용·투표
→ 최종 결과·설문·방 종료
```

오늘의 완료는 P0 전체나 운영 배포 완료가 아니라, 위 교사·학생 여정이 로컬에서 실제 데이터로 이어지는 상태를 의미한다.

- 1·2일차 퀴즈와 보상
- 소득세, 예금, 투자, 금융세, 금융 원장

- 로컬 실행, 자동 테스트, 전체 여정 리허설

- 관리자 로그인·라우트·화면·대시보드

## 3. 기술 기준

- Frontend: Vue 3, TypeScript, Vite, Vue Router, Pinia, Axios
- Backend: Java 21, Spring Boot 4.1.x, Spring MVC, Security, JPA, Flyway
- Database: PostgreSQL 17
- Local infrastructure: Docker Compose
- Synchronization: 2초 주기 `syncVersion` 기반 폴링
- Repository: 프론트·백엔드·인프라 모노레포
- Money: `BIGINT`
- Identifier: `UUID`
- Time: `TIMESTAMPTZ`
- Metadata: `JSONB`

## 5. 구현 원칙

### 단계별 수직 구현

각 개발 단계는 가능하면 다음 순서를 한 번에 완료한다.

```text
Flyway 스키마·데모 데이터
→ 엔티티·서비스·API
→ 프론트 API·Pinia 스토어
→ 교사·학생 화면
→ 백엔드 단위·통합 테스트
→ 프론트 컴포넌트 테스트
→ 두 브라우저 수동 검증
```

### 거래와 상태 변경

- 정산·구매·예금·투자·물가상승·투표에는 `Idempotency-Key` 또는 DB 고유 제약을 적용한다.
- 잔액과 재고는 음수가 될 수 없다.
- 금융 거래는 `financial_transactions`와 `financial_entries`에 남긴다.
- 교사 명령은 `expectedVersion`으로 충돌을 감지한다.
- 경제 상태 변경 후 `syncVersion`을 증가시킨다.
- 마감·정산·물가상승·투표 마감·방 종료처럼 되돌릴 수 없는 작업은 일반 단계 이동과 분리한다.
- 완료 조건을 충족하지 않은 단계 이동은 백엔드에서 차단한다.

### 로컬 우선 범위

- 방 설정은 방 이름과 학생 인원만 입력하고 나머지 규칙은 기본값을 적용한다.
- 교육 자료는 고정 콘텐츠로 제공하며 편집기는 만들지 않는다.
- 투자 시나리오는 로컬 기본 시나리오를 사용한다.
- 설문 응답은 저장하지 않고 외부 링크만 제공한다.

## 6. 목표 여정

### 1일차

1. 교사가 방 이름과 학생 인원을 입력해 방을 생성한다.
2. 시스템이 학생별 참여 코드를 생성한다.
3. 학생이 코드로 입장하고 닉네임·비밀번호를 설정한다.
4. 교사가 접속 인원을 확인하고 퀴즈를 시작한다.
5. 학생이 6문제를 제출하고 교사가 퀴즈를 마감한다.
6. 교사가 소득·세금 정산을 한 번 실행한다.
7. 학생이 자기 월급명세서를 확인한다.
8. 교사가 금융지식·상점·예금·투자 안내 페이지를 제어한다.
9. 학생이 자유 활동에서 상점·예금·투자·지갑을 이용한다.
10. 교사가 마감 미리보기를 확인하고 1일차를 마감한다.
11. 학생은 확정된 1일차 결과를 확인한다.

### 2일차

1. 학생이 참여 코드와 비밀번호로 다시 로그인한다.
2. 교사가 2일차를 시작하고 금융 정산 미리보기를 확인한다.
3. 교사가 예금·투자·금융세 정산을 한 번 실행한다.
4. 학생이 원금·이자·손익·금융세·정산 후 잔액을 확인한다.
5. 학생이 5문제 복습 퀴즈를 제출하고 교사가 보상을 정산한다.
6. 교사가 금융세·인플레이션 교육 페이지를 제어한다.
7. 교사가 상품 가격에 물가상승률 10%를 한 번 적용한다.
8. 학생이 변경된 가격으로 최종 소비를 진행한다.
9. 교사가 공동비용을 적용하고 공동기금 투표를 연다.
10. 학생이 한 표를 제출하고 교사가 투표를 마감한다.
11. 학생과 교사가 최종 결과를 확인한다.
12. 학생이 외부 설문 링크를 열고 교사가 방을 종료한다.

## 7. 이후 개발 단계

### 7단계. 교사 방 생성·참여 코드·대기실

구현:

- 교사 방 생성 API와 최소 입력 화면
- 학생 인원만큼 고유 참여 코드 생성
- 방별 기본 규칙·1일차 세션·퀴즈·상품 생성
- 교사 방 목록과 참여 코드 목록
- 학생 번호·닉네임·접속 상태 표시
- 새 방에 대한 소유권 검사

완료 기준:

- 교사가 새 방을 만든다.
- 생성된 코드로 학생 2명 이상이 입장한다.
- 교사 화면에서 접속 인원이 2초 안에 반영된다.
- 다른 교사의 방은 조회하거나 제어할 수 없다.

### 8단계. 퀴즈 시작·마감과 교육 화면 동기화

구현:

- 퀴즈 `READY → OPEN → CLOSED` 제어
- 닫힌 퀴즈 답안 저장·제출 차단
- 금융지식 주제·페이지 고정 콘텐츠
- 교사 이전·다음 페이지 제어
- 학생 교육 화면 동기화
- 자유 활동 중 학생의 금융지식 다시 보기
- 1일차 금융지식·상점·예금·투자 안내 화면

완료 기준:

- 교사가 퀴즈를 열기 전과 닫은 후에는 학생이 제출할 수 없다.
- 교사가 교육 페이지를 바꾸면 학생 화면도 2초 안에 바뀐다.
- 자유 활동에서는 학생이 교육 주제를 직접 다시 볼 수 있다.

### 9단계. 자유 활동 홈·지갑·거래 내역·예금

구현:

- 자유 경제활동 홈과 활동 선택 카드
- 사용 가능 잔액·예금액·투자액·구매 수 표시
- 학생 자기 거래 내역
- 예금 임시 저장·취소·확정
- 최소 20비빔·10비빔 단위·잔액 검증
- 예상 이자·만기 반환액 표시
- 확정 시 지갑에서 예금 계정으로 원금 이동
- 확정 후 변경·취소 차단

완료 기준:

- 학생이 상점·예금·투자·금융지식·지갑 화면을 이동할 수 있다.
- 예금 확정 요청을 반복해도 원금이 한 번만 이동한다.
- 잔액 부족이나 잘못된 단위에서는 아무 거래도 생성되지 않는다.

### 10단계. 투자·분산투자·시나리오 고정

구현:

- 투자처 3개와 위험도·설명·수익 범위
- 방별 기본 투자 시나리오와 투자처별 수익률
- 1~3개 투자처에 10비빔 단위 배분
- 투자 초안 저장·취소·확정
- 총투자금·투자 후 잔액·손실 가능성 표시
- 확정 시 투자처별 원금 저장과 지갑 차감
- 최초 투자 확정 시 방의 시나리오 고정

완료 기준:

- 학생이 한 곳 또는 여러 곳에 분산투자할 수 있다.
- 총투자금이 잔액을 초과할 수 없다.
- 확정 요청을 반복해도 원금이 한 번만 이동한다.
- 확정 후 투자 금액과 시나리오는 변경되지 않는다.

### 11단계. 1일차 요약·마감

구현:

- 학생 1일차 요약: 잔액·예금·투자·구매 상품
- 교사 자유 활동 집계: 상점·예금·투자·미활동 인원
- 마감 미리보기: 미제출·미정산·미확정·처리 중 거래
- 명시적인 `CLOSE_DAY1` 명령
- 예금·투자 초안 자동 취소
- 확정된 예금·투자와 투자 시나리오 고정
- 상점·예금·투자 신규 거래 차단
- 1일차 세션과 방 상태 마감

완료 기준:

- 필수 정산이 끝나지 않으면 마감할 수 없다.
- 마감 후 모든 1일차 경제활동 API가 거래를 거부한다.
- 학생은 활동을 하지 않았더라도 정상적인 마감 결과를 확인한다.
- 일반 단계 이동으로 마감 규칙을 우회할 수 없다.

### 12단계. 2일차 시작·금융 정산·개인 결과

구현:

- 명시적인 `START_DAY2` 명령과 2일차 세션 활성화
- 기존 코드·비밀번호 재로그인과 자산 복구
- 예금 원금·이자 계산
- 투자처별 원금·수익률·손익 계산
- 예금 이자와 양수인 투자 순이익에 금융세 10% 적용
- 금융세 공동기금 적립
- 교사 금융 정산 미리보기·실행
- 학생 개인 금융 결과 화면
- 2일차 신규 예금·투자 차단

완료 기준:

- 서버와 브라우저를 재시작해도 1일차 데이터가 유지된다.
- 금융 정산 요청을 반복해도 원금·이자·손익·세금이 한 번만 반영된다.
- 정산 실패 시 방 전체에 일부 결과만 남지 않는다.
- 예금이나 투자를 하지 않은 학생도 정상 결과를 받는다.

### 13단계. 2일차 복습 퀴즈·보상 정산

구현:

- 2일차 객관식 퀴즈 5문제
- 퀴즈 시작·마감과 학생 제출
- 참여수당 10비빔
- 정답당 5비빔 보상
- 교사 제출 현황과 보상 미리보기
- `DAY2_QUIZ_REWARD` 정산과 금융 원장 기록

완료 기준:

- 1일차와 2일차 퀴즈·답안·제출이 섞이지 않는다.
- 동일 보상 정산을 반복해도 지갑이 한 번만 증가한다.
- 미제출 학생 경고 후 교사가 다음 단계 이동 여부를 결정할 수 있다.

### 14단계. 금융세·인플레이션 교육·물가상승·최종 상점

구현:

- 금융세·위험과 수익·인플레이션 교육 페이지
- 교사 물가상승 미리보기
- `기존 가격 × 1.1` 정수 반올림
- 방당 한 번만 물가상승 적용
- 기존 가격과 현재 가격 함께 표시
- `DAY2_FINAL_SHOP`에서 상점 재개방
- 2일차에는 상점·금융지식·지갑만 이용 가능

완료 기준:

- 물가상승 요청을 반복해도 가격이 한 번만 변경된다.
- 이미 완료된 구매 가격은 바뀌지 않는다.
- 1일차 자유 활동과 2일차 최종 상점에서만 구매할 수 있다.
- 최종 상점에서는 예금·투자를 새로 확정할 수 없다.

### 15단계. 공동기금 비용·투표

구현:

- 소득세·금융세·조정 금액이 반영된 공동기금 조회
- 기본 공동비용 선택지와 적용 후 예상 잔액
- 교사 공동비용 적용
- 투표 선택지와 교사 투표 시작·마감
- 학생당 한 표 제출
- 익명 집계와 마감 후 결과 공개
- 동점 시 교사 최종 선택

완료 기준:

- 공동비용이 공동기금 잔액을 초과할 수 없다.
- 같은 학생이 두 번 투표할 수 없다.
- 투표 중에는 개인 선택을 공개하지 않는다.
- 마감 전후의 투표 가능 상태가 정확히 적용된다.

### 16단계. 최종 결과·설문·방 종료

구현:

- 학생 최종 명세서: 소득·세금·예금·투자·소비·최종 잔액
- 구매 상품과 공동기금 투표 결과
- 교사 반 전체 요약과 학생별 결과
- 교사 상품 배부 목록
- 외부 구글폼 링크
- 명시적인 `COMPLETE_ROOM` 명령
- 종료 시 모든 거래와 상태 변경 차단
- 종료 후 결과 조회 유지

완료 기준:

- 학생과 교사가 같은 원장 데이터를 기준으로 결과를 확인한다.
- 설문은 새 탭에서 열리고 응답 내용은 서비스에 저장하지 않는다.
- 방 종료 후 구매·정산·투표·단계 이동이 모두 차단된다.
- 새로고침이나 재로그인 후에도 최종 결과를 다시 볼 수 있다.

### 17단계. 안정화·복구·전체 리허설

구현:

- 프론트 로딩·빈 상태·오류·재시도 화면
- 네트워크 끊김·재연결 안내
- 요청 중 버튼 비활성화와 중복 클릭 방지
- 폴링 실패 후 자동 복구
- 모든 금액 변경 요청의 멱등성 회귀 테스트
- 구매 동시성·재고·잔액 테스트
- 서버 재시작과 PostgreSQL 데이터 유지 확인
- 로컬 테스트 데이터 초기화 방법 문서화
- 교사 1명·학생 2명 이상의 1·2일차 전체 리허설 2회

완료 기준:

- 새로고침·재로그인·일시적 네트워크 오류 후 현재 화면이 복구된다.
- 잔액·재고·정산·투표가 중복 처리되지 않는다.
- 치명적인 브라우저 콘솔·백엔드 오류 없이 전체 여정을 두 번 완료한다.
- 첫 번째 리허설의 1일차 데이터가 2일차까지 유지된다.

## 8. 추가 데이터베이스 범위

현재 V1~V7 스키마를 유지하며 필요한 테이블을 단계별 Flyway 마이그레이션으로 추가한다.

- 교육: `learning_topics`, `learning_pages` 또는 기존 `module_states`와 결합한 동등 구조
- 예금: `deposits`
- 투자: `investment_assets`, `investment_scenarios`, `investment_scenario_returns`, `investment_orders`, `investment_allocations`
- 공동기금: `fund_cost_options`, `fund_expenses`
- 투표: `vote_sessions`, `vote_options`, `votes`

최종 결과는 가능한 한 금융 원장과 확정된 도메인 테이블에서 계산한다. 별도 결과 스냅샷이 필요한 경우에도 원장 데이터를 원본으로 유지한다.

## 9. 로컬 데모 데이터

`local` 프로필에서만 다음 기본값을 제공한다.

- 교사 계정 1개
- 기존 데모 방 1개와 새 방 생성 기능
- 방당 기본 학생 코드 3개 또는 교사가 입력한 인원만큼의 코드
- 1일차 퀴즈 6문제
- 2일차 퀴즈 5문제
- 상품 3개
- 투자처 3개와 기본 시나리오 1개
- 공동비용·투표 기본 선택지
- 역할 소득 100비빔
- 1일차 참여수당 10비빔, 정답당 10비빔
- 2일차 참여수당 10비빔, 정답당 5비빔
- 소득세·예금 이율·금융세·물가상승률 각 10%
- 외부 설문 테스트 URL

운영 프로필에서는 데모 계정과 시드 데이터를 만들지 않는다.

## 10. 자동 테스트

### 공통 상태·권한

- 방 소유자가 아닌 교사 접근 차단
- 허용되지 않은 단계 이동 `409 STATE_CONFLICT`
- 마감·종료 후 경제활동 차단
- 새로고침 후 현재 단계·자산 복구

### 금융·정산

- 소득·예금·투자·퀴즈 보상 정산 중복 실행 차단
- 예금·투자 확정 후 지갑과 전용 계정 동시 변경
- 잔액 부족 시 전체 롤백
- 금융세 계산과 공동기금 적립
- 금융활동을 하지 않은 학생의 정산

### 상점·인플레이션

- 동시 구매 시 재고 음수·초과 판매 없음
- 구매 실패 시 잔액·재고·구매 기록 전체 롤백
- 동일 구매 재요청 시 기존 결과 반환
- 물가상승 방당 1회 적용
- 1일차 구매 가격 불변

### 투표

- 학생당 한 표 고유 제약
- 마감 후 투표 차단
- 익명 결과 집계
- 공동기금 잔액 초과 비용 차단

## 11. 수동 통합 테스트

교사와 학생을 서로 다른 브라우저 창에서 실행한다.

### 1일차

1. 교사가 방을 만들고 코드를 확인한다.
2. 학생 2명이 서로 다른 코드로 가입한다.
3. 퀴즈 시작·제출·마감과 소득 정산을 진행한다.
4. 학생 월급명세서와 교육 화면 동기화를 확인한다.
5. 한 학생은 상점·예금·투자를 모두 이용한다.
6. 다른 학생은 일부 또는 아무 활동도 하지 않는다.
7. 교사가 1일차를 마감하고 신규 거래 차단을 확인한다.

### 2일차

1. 브라우저 또는 서버를 재시작한 뒤 학생이 다시 로그인한다.
2. 교사가 금융 정산을 실행하고 학생 결과를 확인한다.
3. 복습 퀴즈와 보상 정산을 진행한다.
4. 교육 후 물가상승을 적용하고 최종 구매를 진행한다.
5. 공동비용 적용과 학생 투표를 진행한다.
6. 최종 결과·설문 링크를 확인하고 방을 종료한다.
7. 종료 후 모든 쓰기 요청이 차단되는지 확인한다.

## 12. 최종 완료 조건

- README 명령만으로 PostgreSQL·백엔드·프론트엔드를 실행할 수 있다.
- 교사가 새 방과 참여 코드를 생성할 수 있다.
- 학생이 1일차 가입과 2일차 재로그인을 할 수 있다.
- 교사 단계·퀴즈·교육 화면 제어가 학생에게 2초 안에 반영된다.
- 1일차 소득·세금·상점·예금·투자가 실제 원장으로 이어진다.
- 1일차 마감 후 데이터가 고정되고 신규 거래가 차단된다.
- 2일차 금융 정산·퀴즈 보상·물가상승·최종 소비가 동작한다.
- 공동기금 비용과 1인 1표 투표가 동작한다.
- 학생 최종 명세서와 교사 반 결과가 일치한다.
- 방 종료 후 결과는 유지되고 모든 쓰기 작업은 차단된다.
- 중복 클릭·재시도·새로고침·서버 재시작으로 돈과 재고가 중복 변경되지 않는다.
- 전체 1·2일차 여정을 로컬에서 두 번 완료한다.

## 13. 일정이 밀릴 때 줄이는 순서

1. 디자인 세부 조정
2. 교사 상품·공동비용 편집 기능을 기본값으로 대체
3. 교육 페이지 수 축소
4. 투자 시나리오를 기본값 1개로 고정
5. 교사 이전 단계 이동 축소
6. 상품을 3개에서 1개로 축소

다음 항목은 줄이지 않는다.

- PostgreSQL 실제 연결과 금융 원장
- 교사 단계 제어와 학생 화면 동기화
- 예금·투자·구매의 원자성과 멱등성
- 1일차 마감과 2일차 데이터 복구
- 2일차 금융 정산·물가상승
- 공동기금 1인 1표
- 방 종료 후 거래 차단

부분 정산 재처리, 복잡한 설정 마법사, 고급 통계, 운영 배포는 로컬 전체 여정이 완성된 뒤 별도 단계로 다룬다.

## 14. Git·팀 협업 기준

- 한 개발 단계는 가능한 한 하나의 기능 단위 커밋으로 마무리한다.
- 프론트와 백엔드 계약이 바뀌면 같은 단계 안에서 함께 반영한다.
- Flyway 마이그레이션 파일은 이미 적용된 번호를 수정하지 않고 새 번호를 추가한다.
- 관리자 담당 팀원이 만든 라우트·화면·API 파일은 수정하지 않는다.
- 공용 스키마·보안 설정·라우터를 함께 수정해야 할 때는 변경 내용을 먼저 공유한다.
- 관리자 영역에서 사용할 수 있도록 방 상태·거래·정산 결과는 공용 도메인 데이터에 정확히 저장한다.

성공 기준은 화면 개수가 아니라, 교사와 학생의 2일 여정이 실제 PostgreSQL 데이터로 이어지고 같은 요청을 반복해도 돈·재고·정산·투표가 중복 변경되지 않는 것이다.
