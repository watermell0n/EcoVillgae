# 교실 부동산·청약 모듈 구현 계획

- 작성일: 2026-08-06
- 대상 브랜치: `develop`
- 참고 서비스: [ClassCoin](https://classcoin.me/)
- 핵심 원칙: 부동산은 독립 모듈이고, 청약은 부동산 위에 선택적으로 붙는 확장 모듈이다.

## 1. 제품 정의

### 부동산 모듈

교실의 실제 좌석을 경제 활동용 자산으로 표시하고, 학생이 학급 화폐로 자리 이용권을 사고 재판매할 수 있게 한다. 화면에서는 친숙하게 `내 자리`, `소유`, `매물`이라는 표현을 쓰되, 실제 법적 소유권이 아니라 해당 학급에서만 유효한 자리 이용권임을 안내한다.

MVP 범위는 다음과 같다.

- 교사가 좌석 배치도와 판매 대상 좌석을 만든다.
- 교사가 최초 판매 가격과 이용 기간을 정해 직판 매물로 공개한다.
- 학생은 잔액이 충분하면 공개된 자리를 구매한다.
- 소유 학생은 자리를 재판매 매물로 등록하고 다른 학생이 구매할 수 있다.
- 학생당 활성 자리 이용권은 최대 1개, 좌석당 활성 소유자는 최대 1명이다.
- 모든 구매·재판매는 지갑 원장과 소유권 변경을 하나의 트랜잭션으로 처리한다.
- 교사는 학습·안전상 필요한 경우 사유와 환급 규칙을 남기고 권리를 회수할 수 있다.

월세·전세·임대는 현재 코드와 DB에 흔적이 있지만 이번 1차 MVP의 핵심은 아니다. 구매·재판매와 청약 흐름이 안정화된 뒤 별도 확장으로 다룬다.

### 청약 모듈

부동산 모듈이 활성화된 학급에서만 사용할 수 있는 선택 확장이다. 교사가 좌석의 공급 방식을 `직판` 대신 `청약`으로 선택할 수 있게 한다.

- 학생은 청약통장을 개설하고 학급 화폐를 납입한다.
- 교사는 대상 좌석, 고정 분양가, 신청 기간, 최소 납입 횟수와 최소 잔액을 설정한다.
- 학생은 조건을 충족한 청약에 신청한다.
- 신청 시 분양가를 청약통장 잔액에서 예약해 중복 사용을 막는다.
- MVP 선정 방식은 조건 충족자 대상 공개 무작위 추첨으로 통일한다.
- 당첨자는 예약 금액이 판매 계정으로 정산되고 자리 이용권을 받는다.
- 미당첨자는 예약만 해제되며 청약통장 잔액은 유지된다.
- 신청·선정 결과에는 개인 잔액이나 다른 학생의 이름을 공개하지 않는다.

## 2. 모듈 조합별 운영 시나리오

| 부동산 | 청약 | 운영 방식 | 화면 동작 |
| --- | --- | --- | --- |
| OFF | OFF | 자리배치도 사용 안 함 | 부동산·청약 메뉴와 관련 API 비활성화 |
| ON | OFF | 직판과 학생 간 재판매만 사용 | 부동산·내 자리·매물 화면 표시, 청약 탭과 API 호출 숨김 |
| ON | ON | 직판·재판매에 청약 공급 방식 추가 | 부동산 화면에 청약 탭·통장·모집 공고 표시 |
| OFF | ON | 허용하지 않음 | 활성화 시 `PREREQUISITE_MODULE_REQUIRED` 반환 |

### 활성화·비활성화 전환 규칙

- 청약 활성화는 부동산이 이미 `ACTIVE`일 때만 허용한다.
- 부동산이 비활성화된 학급은 좌석 배치도를 생성·조회하지 않으며 관련 화면을 노출하지 않는다.
- 청약 비활성화는 열린 모집과 처리 중인 신청이 없을 때만 허용한다.
- 청약을 꺼도 이미 당첨·정산된 자리 권리는 부동산 모듈에서 유지한다. 청약 이력은 읽기 전용으로 보존한다.
- 청약이 활성화된 동안 부동산 비활성화는 금지한다.
- 부동산 비활성화는 열린 직판·재판매 매물, 처리 중 계약, 활성 청약이 모두 정리된 뒤에만 허용한다.
- 모듈을 다시 켜도 이전 권리·거래·청약 이력을 재사용하며 중복 자산을 만들지 않는다.

## 3. 핵심 사용자 흐름

### 시나리오 A: 부동산만 사용하는 학급

1. 교사가 부동산 모듈을 활성화한다.
2. 좌석 배치도를 만들고 판매 가능한 좌석과 가격을 정한다.
3. 학생이 자리 지도를 보고 공개 매물을 선택한다.
4. 서버가 잔액, 모듈 상태, 학생·좌석 중복 소유, 상태 버전을 확인한다.
5. 지갑 차감과 자리 권리 배정을 원자적으로 커밋한다.
6. 소유 학생이 재판매 가격을 정해 매물로 등록한다.
7. 다른 학생이 구매하면 판매자 지갑 입금과 소유권 이전을 원자적으로 커밋한다.

### 시나리오 B: 부동산과 청약을 함께 사용하는 학급

1. 교사가 부동산 활성화 후 청약 모듈을 활성화한다.
2. 학생이 청약통장을 개설하고 학급 화폐를 납입한다.
3. 교사가 특정 좌석을 청약 공급으로 공개한다.
4. 조건을 충족한 학생이 신청하고 분양가가 통장 안에서 예약된다.
5. 신청 종료 후 교사가 추첨을 실행한다.
6. 당첨자 정산·권리 배정과 미당첨자 예약 해제를 한 트랜잭션으로 처리한다.
7. 당첨 이후의 소유·재판매는 부동산 모듈의 일반 규칙을 따른다.

### 시나리오 C: 운영 중 청약을 끄는 학급

1. 열린 모집이 있으면 교사가 취소하고 모든 예약 금액을 해제한다.
2. 처리 중 신청이 없음을 확인한다.
3. 청약 모듈을 비활성화한다.
4. 학생 화면에서 청약 탭과 통장 작업을 숨긴다.
5. 기존 당첨자의 자리 권리와 재판매 기능은 그대로 유지한다.

## 4. 현재 `develop` 구현 진단

이미 존재하는 기반:

- `V1_22__property_and_subscription.sql`에 좌석 자산, 계약, 임대 매물, 청약 공고·신청·통장 테이블이 있다.
- `PropertyService`와 `PropertyController`에 배치도, 자산, 계약, 청약 공고 생성·신청·추첨, 청약통장 API가 있다.
- 학생 앱에 부동산 화면과 청약통장 UI가 있다.
- 모듈 카탈로그에 `HOUSING_SUBSCRIPTION -> REAL_ESTATE` 선행 관계가 등록되어 있다.
- OpenAPI와 HTTP API 문서에 관련 계약이 정의되어 있다.

현재 막혀 있는 사용자 흐름과 정책 불일치:

- 교사용 좌석·매물·계약·청약 관리 화면이 없다.
- 학생이 청약 공고 목록을 조회하거나 실제로 신청할 API/UI 연결이 없다.
- 학생 간 재판매 등록·구매 흐름이 없다. 기존 목록 기능은 월세·전세 중심이다.
- 청약 취소, 신청 취소, 열린 공고 조회, 교사용 신청 집계 API가 없다.
- 현재 추첨은 단순 셔플이고, 신청 금액 예약·당첨 정산·미당첨 해제가 구현되어 있지 않다.
- 부동산·청약 모듈 중지 시 열린 거래와 의존 모듈을 검사하는 차단 규칙이 없다.
- 쓰기 요청의 `expected_state_version`을 컨트롤러가 받지만 서비스가 대부분 검증하지 않는다.
- 부동산 패키지 전용 백엔드 테스트가 없다.
- 기존 정책 문서는 기간형 좌석 이용권, 현재 DB·API는 월세·전세·매매를 중심으로 하여 기준을 하나로 맞춰야 한다.

## 5. 권장 도메인 상태

### 좌석 자산

```text
DRAFT -> OPEN_DIRECT -> OWNED -> LISTED_RESALE -> OWNED
      -> OPEN_SUBSCRIPTION -> OWNED
OWNED -> RETURNED | INACTIVE
```

- `OPEN_DIRECT`: 최초 직판
- `OPEN_SUBSCRIPTION`: 청약 모집 중
- `OWNED`: 학생이 활성 이용권 보유
- `LISTED_RESALE`: 소유자가 재판매 매물 게시
- `RETURNED`: 반납·기간 종료·교사 회수

### 청약 공고

```text
DRAFT -> OPEN -> CLOSED -> DRAWN
              -> CANCELED
```

### 청약 신청

```text
APPLIED -> WON | LOST | CANCELED
WON -> SETTLED
```

DB에서는 학생당 활성 권리 1개, 좌석당 활성 권리 1개, 좌석당 열린 공급 활동 1개를 부분 유니크 인덱스로 강제한다.

## 6. API 보강안

기존 API를 최대한 유지하면서 다음 계약을 추가·수정한다.

- `GET /classrooms/{classroom_id}/subscription-offers`: 학생·교사용 공고 목록
- `GET /classrooms/{classroom_id}/property-contracts`: 교사용 대기 계약 목록
- `GET /classrooms/{classroom_id}/subscription-offers/{offer_id}/applications`: 교사용 익명 집계·신청 상태
- `POST /subscription-offers/{offer_id}/cancel`: 공고 취소와 예약 해제
- `DELETE /students/me/subscription-applications/{application_id}`: 마감 전 신청 취소
- `POST /students/me/properties/{property_id}/sale-listings`: 재판매 매물 등록
- `PUT /sale-listings/{listing_id}` / `DELETE /sale-listings/{listing_id}`: 재판매 수정·취소
- `POST /sale-listings/{listing_id}/purchase`: 재판매 원자 구매
- 부동산·청약의 모든 쓰기 API에 멱등 키와 `expected_state_version` 검증 적용

학생용 조회 응답은 청약 모듈 활성 여부를 포함하고, 비활성일 때 청약 전용 필드를 생략하거나 기능 비활성 상태로 명시한다.

## 7. UI 구현안

### 교사용 웹

- 모듈 설정에서 부동산과 청약을 별도 카드로 표시하고 선행 관계를 안내한다.
- 좌석 배치 편집: 행·열 생성, 판매 제외 좌석, 표시명, 가격 설정
- 좌석 상세: 직판 또는 청약 공급 선택
- 거래 관리: 대기 계약, 활성 소유권, 재판매 매물, 강제 회수
- 청약 관리: 공고 생성, 신청자 수, 마감, 추첨, 취소

### 학생 앱

- `자리 지도`: 판매 가능·청약 중·소유·내 자리 상태를 색상과 문구로 구분
- `내 자리`: 현재 권리, 구매 가격, 재판매 등록·취소
- `매물`: 교사 직판과 학생 재판매 목록
- `청약`: 모듈이 활성화된 경우에만 통장, 모집 공고, 신청·취소, 결과 표시
- 공개 화면에는 다른 학생 이름, 잔액, 개인 순위를 노출하지 않는다.

## 8. 구현 순서

### 1단계 — 계약·모듈 경계 정리

- 정책 문서, OpenAPI, DB 상태명을 하나의 모델로 통일한다.
- 부동산 단독/부동산+청약 조합 테스트를 먼저 작성한다.
- 모듈 활성화·비활성화 차단 규칙을 구현한다.

완료 기준: 청약 없이 부동산 API 전체가 동작하고, 청약 단독 활성화 및 잘못된 중지 순서가 거절된다.

### 2단계 — 부동산 단독 수직 기능

- 교사 좌석 설정·직판 공개
- 학생 원자 구매
- 학생 재판매 등록·구매
- 소유권·지갑·상태 버전·멱등성 테스트
- 교사용/학생용 최소 UI 연결

완료 기준: 청약 모듈을 켜지 않은 학급에서 좌석 생성부터 재판매까지 E2E로 완료된다.

### 3단계 — 청약 확장

- 공고 조회·신청·취소 API
- 청약통장 금액 예약
- 추첨·당첨 정산·미당첨 예약 해제
- 청약 활성/비활성 전환과 이력 보존
- 교사용 청약 관리·학생용 청약 탭 연결

완료 기준: 청약을 켠 학급에서 공고 생성부터 당첨자 소유권 배정까지 E2E로 완료된다.

### 4단계 — 운영 안정화

- 트랜잭션 동시성, 원장 실패 롤백, 멱등 재시도 테스트
- 커밋 후 실시간 이벤트와 화면 갱신
- 감사 로그, 개인정보 노출 검사
- 만료·교사 회수·학급 종료 정산
- API 스키마와 구현 일치 검사

## 9. 필수 검증 시나리오

- 부동산 ON, 청약 OFF에서 직판·재판매 성공
- 부동산 OFF 상태에서 청약 활성화 거절
- 청약 ON 상태에서 부동산 중지 거절
- 청약 중지 후 기존 당첨자의 자리와 재판매 기능 유지
- 동일 좌석 동시 구매 시 단 한 명만 성공
- 이미 자리를 가진 학생의 추가 구매·청약 거절
- 잔액 부족 시 지갑·소유권 모두 무변경
- 재판매 시 구매자 차감·판매자 입금·소유권 이전이 원자적으로 처리
- 중복 청약 신청 거절
- 청약 신청 금액 중복 사용 방지
- 추첨 재시도 시 동일 결과 반환
- 공고 취소 시 모든 예약 금액 해제
- 학생·공개 응답에서 다른 학생의 이름·잔액·개인 순위 미노출

## 10. 기준선 검증 메모

현재 환경에서는 Gradle 9.5.1 배포 파일이 로컬에 없어 테스트 실행 시 외부 다운로드가 필요하다. 구현에 착수할 때 의존성 다운로드 승인을 받은 뒤 백엔드 전체 테스트를 기준선으로 기록한다. 학생 앱 의존성도 정리 과정에서 삭제했으므로 `pnpm install` 후 타입 검사와 화면 테스트를 수행한다.
